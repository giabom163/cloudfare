## 一、为什么会在 Cloudflare Worker 上做这件事

先讲清动机，不然后面所有取舍都不合理。

### 1.1 起点：OpenCode Go 套餐的真实约束

`opencode.ai/zen/go/v1` 是第三方网关，不是 OpenAI 官方。要用它，绕不开三件事：

| 约束 | 后果 | 谁能解决 |
|---|---|---|
| **key 暴露** | 客户端要直连上游，key 就在 config 里 | Worker |
| **地区封锁** | 国内 IP 直连被 CF 判 403 | 需要能控制出口 |
| **协议分裂** | GPT/Luna 只认 `/responses`，国产系只认 `/chat/completions` | Worker |

前两件是网络问题，第三件是协议问题——**Worker 只解决了第三件，第二件没解决**。

### 1.2 CC Switch 解决不了协议分流

关键约束在 CC Switch 的设计里：

> **apiFormat 是卡级开关，无法按模型分流。**

意思是一张卡上只能设一种协议格式。但 OpenCode 上游要求按模型走不同协议。所以这张卡如果设成 `responses`，glm/kimi/deepseek 全会 400；设成 `chat`，GPT/Luna 全会失败。

**这就是 Worker 存在的唯一理由**：在卡级开关之上，加一层按模型的协议分流。

### 2.1 责任划分表

| 层 | 该做 | 不该做 | 实际踩过的坑 |
|---|---|---|---|
| **Codex** | 只管发请求 | 不该知道 key 是谁的 | 误以为它读 cc-switch.db |
| **CC Switch** | 路由/熔断/usage | **不该承担协议分流**（做不到） | 曾被当作万能中间件 |
| **Worker** | 协议桥接/洗头/传 key | **不该假装成功** | v10 假成功 → v12 回退 |
| **上游** | 推理 | — | 推理池抖动、配额、限流 |

### 2.2 Worker 内部四条路径

| 路径 | 入口 | 适用 | 关键纪律 |
|---|---|---|---|

## 三、协议桥接的原理（最核心的部分）

### 3.1 为什么必须做

```
Codex  ──写 /responses──▶  Worker  ──写 /chat/completions──▶  上游
       ◀──responses SSE──          ◀──chat SSE──
```

两套协议在**请求体、响应体、工具调用、usage 统计**四个维度都不同，必须双向翻译。

### 3.2 模型识别靠前缀，不是能力探测

```ts
const CHAT_MODEL_RE = /^(glm-|kimi-|deepseek-|mimo-|minimax-)/i;
```

代码注释写得很清楚：

> 目录同步会暴露更多模型，但不能仅凭「模型能被列出」推断其协议能力。
> qwen/gpt/grok 及其他未知模型保持 Responses，待能力确认后再加入桥接名单。

**这是有意保守**——宁可漏判走原生（报 400 但看得懂），也不误判走桥接（静默出错难排查）。

### 3.3 桥接的四个翻译点

| 维度 | responses → chat | chat → responses |
|---|---|---|
| 请求体 | `input` → `messages`，`instructions` → system | 反向 |
| 流式事件 | — | `chat.chunk` → `response.output_text.delta` 等 |
| 工具调用 | `function_call` → `tools`/`tool_calls` | 反向，`arguments` 需 JSON 解析还原 |
| usage | `input_tokens`/`output_tokens` | `prompt_tokens`/`completion_tokens` |

对应函数：
- 请求转换：`responsesToChatRequest(rb)`（L426 调用）
- 响应流转换：`makeChatToResponsesStream(model)`（L208 定义，L475 应用）
- 事件守卫：`makeResponsesStreamGuard(model, abort)`（L725）

### 3.4 保活为什么必需

```
上游 30 秒没吐字节
  ↓
Codex SSE 空闲判定 → Reconnecting
  ↓
重连重发整个大上下文（含全部历史）
  ↓
input token 重复计费 ★ 这才是烧额度的真凶
```

解法（L725 guard）：

| 机制 | 频率 | 作用 |
|---|---|---|
| keepalive 注入 | 3s 无数据 | `: keepalive\n\n` SSE 注释，客户端解析器忽略但保连接 |
| idle abort | 60s 无数据 | 真的 hang 了才中断，避免 Worker 实例空转 |
| `seenCompleted` | 一次性 | 防重复发 `response.completed` |

**注意 keepalive 不重置 idle 计时器**——否则一个 hang 住的上游能靠 keepalive 永远不被发现。

## 四、故障分层与排查顺序

### 4.1 关键认知：观测点决定结论

| 观测点 | 能看到 | 看不到 |
|---|---|---|
| `cc-switch.log` | 谁在发、目标 URL、模型名 | **上游返回码** |
| OpenCode Console | 返回码/耗时/token/计费 | 请求来源 |
| `wrangler deployments list` | 线上跑的是哪个版本 | 代码内容 |
| `git log` | 本地代码演进 | 线上是否部署 |

**今天踩的坑**：只看 cc-switch.log 就说「22 点零错误」，被 Console 截图直接推翻（22:03-22:04 大量 `208 inference_failed`）。

**规矩**：本地日志说「发过了」时，**必须去 Console 确认「返回了什么」**。不一致时以 Console 为准。

### 4.2 排查决策树

```
报错
  ↓
Codex 侧: Reconnecting / unexpected status XXX
  ↓
查 cc-switch.log 最后一行
  ├─ 无新行 → CC Switch 没收到请求
  │    ├─ 15721 未监听 → CC Switch 进程死了 → 手动启动
  │    └─ 有请求行但无 FWD-003 → 转发中或已被熔断
  │
  └─ 最后一行是 FWD-003 → 读 upstream_status
       ├─ 403 Country...not supported → CF 边缘地区封锁（换出口 IP）
       ├─ 504 upstream_unavailable → Worker 兜底（可能是代码 bug！查 git）
       ├─ 504 timed out (>60s)      → 上游 60s 无响应（调超时或换模型）
       ├─ 429 GoUsageLimitError     → 周配额打爆（等下周，不可恢复）
       ├─ 429 Token rate limit      → TPM 限流（等窗口自动恢复）
       └─ 401/403 Invalid credential → key 失效或 Authorization 被覆盖
  ↓
查 OpenCode Console 确认实际返回码
  └─ 不一致 → 以 Console 为准（服务端视角）
```

### 4.3 三个「不要」

| 不要 | 后果 |
|---|---|
| 不要用假成功/incomplete 掩盖失败 | Codex 收到「200 但空」→ 表现「没回复=不通」，排查绕大圈 |
| 不要为验证已确认正确的东西发请求 | 每次探测都消耗 token，还可能打爆限流 |
| 不要凭错误文案猜原因 | 「timed out」可能实际是代码崩了（4.1 那次） |

## 五、服务器方案（核心建议）

### 5.1 问题的本质

当前 403 地区封锁的根源：

```
请求 → CF 边缘节点 → CF 按自己的 IP 库判定地区 → 403
```

**你无法控制 Worker 跑在哪个节点、出口 IP 是哪个。** 代码层再怎么改都没用。

### 5.1b 术语澄清（这些概念经常被混用）

| 术语 | 定义 | 常见误解 |
|---|---|---|
| **入口** | 客户端连接到的那个节点 | 入口质量好 ≠ 出口质量好 |
| **线路机** | 负责「到上游的网络质量」的机器 | 线路好 ≠ IP 风控低 |
| **落地机** | 真正向上游发出请求的出口机器 | 落地 IP 才是被上游判定的对象 |
| **数据中心 IP** | VPS 常见出口 | ≠ 一定被拒，但风控权重通常更高 |
| **住宅 / 静态住宅 IP** | 另一类 IP 资源（成本高、稳定性不透明） | 对 API 未必比数据中心 IP 更好 |
| **「纯净度」** | **非标准营销词，无明确定义** | 必须转化为可测指标（如 403 率、可达率） |

**「线路好」和「IP 干净」是两件事。** 本项目的验收应落在**可测量指标**上，而不是标签。

**针对 API / CLI 请求的优先级**（区别于流媒体/注册场景）：

1. 上游可达率
2. 晚高峰丢包与抖动
3. SSE 长连接稳定性
4. 出口国家/地区符合上游策略
5. IP 是否频繁触发拒绝
6. 延迟
7. 「纯净度」等营销概念（最后考虑）

**不要用它承诺**：流媒体解锁、注册登录风控绕过、支付或身份验证、任何需要住宅网络属性的服务。

### 5.2 四个方案对比

> **成本列为公开价格的粗略区间，非本项目实测**。实际价格随地区、线路、带宽、是否含独立 IP 显著变化。

| 方案 | 成本区间 | 出口可控 | 对 403 的作用 | 保留现有功能 | 评价 |
|---|---|---|---|---|---|
| **A. VPS 直连（保留桥接代码）** | ¥30-80/月 | ✅ 是 | ⚠️ **待 A/B 验证** | ✅ | 首选验证路径 |
| B. 换 CF 区域 / 节点 | ¥0 | ❌ 不可控 | ❌ 无效 | ✅ | 已实测无效 |
| C. 加腾讯云 EdgeOne 等 CDN | ¥0-50/月 | ⚠️ 部分 | ⚠️ 不确定 | ✅ | 需改 DNS，须实测 |
| D. 绕过 Worker 直连上游 | ¥0 | ✅ 是 | ⚠️ 不确定 | ❌ 失去 key 隐藏与桥接 | 退回原点 |
| E. Worker 前置 + VPS 后置 | ¥30-80/月 | ✅ 是 | ❌ **Worker 那一跳仍会 403** | ✅ | **花钱解决不了 403** |

**必须提醒的坑（方案 E）**：Worker 自己也要出口到 VPS，**因此 Worker 那一跳仍可能被 403 拦下**。它只适合「想要固定出口但不需要解决 403」的场景。**要验证 403 是否与出口有关，VPS 必须直连上游。**

### 5.3 方案 A 详细设计

**架构**：

```
Codex
  ↓ 127.0.0.1:15721
CC Switch (多卡/熔断/usage 不变)
  ↓ https://你的域名/v1
VPS 反代 (固定出口 IP)
  ↓
opencode.ai/zen/go/v1
```

**VPS 选型（逐项验证，不默认可行）**：

| 项 | 需要确认什么 | 为什么不能默认 |
|---|---|---|
| 出口地区 | **先确认上游实际接受哪些地区** | 不能默认「美区最稳」，上游策略会变 |
| 账号绑定 | 你的账号 / 套餐是否绑定地区 | 换出口未必解决账号侧限制 |
| IP 类型 | 数据中心 IP 是否被目标服务标记 | IP 段信誉影响风控，不是标签决定 |
| 线路 | CN2 GIA / 9929 等优化线路 | 「低延迟」不等于「晚高峰稳定」 |
| 配置 | 1 核 512M 起（纯转发无推理） | — |
| 系统 | Ubuntu 22.04 / Debian 12 | systemd 常驻简单 |

**建议的选型原则**：「选择被上游接受、到上游稳定、到本地客户端可用的出口」，**不是默认选美国**。

**反代实现（最简版）**：

```nginx
server {
    listen 443 ssl;
    server_name your.domain.com;

    ssl_certificate     /etc/letsencrypt/live/your.domain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/your.domain.com/privkey.pem;

    location / {
        proxy_pass https://opencode.ai/zen/go/v1;
        proxy_ssl_server_name on;

        # 关键：SSE 必须关缓冲，否则 keepalive 到不了客户端
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 600s;
        proxy_send_timeout 600s;

        # 透传关键头
        proxy_set_header Host              opencode.ai;
        proxy_set_header Authorization     $http_authorization;
        proxy_set_header x-opencode-session $http_x_opencode_session;
        proxy_set_header User-Agent        $http_user_agent;
    }
}
```

**⚠️ 三个必踩的坑**：

1. **`proxy_buffering off;` 必须有** —— Nginx 默认缓冲会把 SSE 卡住，Worker 辛苦发的 keepalive 到不了 Codex，直接 Reconnecting。
2. **`proxy_read_timeout 600s;`** —— 默认 60s 会掐断长推理。
3. **`proxy_set_header Host opencode.ai;`** —— 不改的话上游可能返回 404。

**关于协议桥接**：

纯 Nginx 不提供 responses↔chat 转换能力。**准确表述**是「纯 Nginx 无法替代本项目的国产模型协议桥接」，而不是「国产模型在任何 Nginx 方案下都不能用」——只要上下游协议一致，或前后端另有桥接层，国产模型仍可使用。

在**当前 CC Switch 统一走 responses 入口**的前提下：

| 方案 | 可用能力 |
|---|---|
| 纯 Nginx | 仅 `/responses` 原样透传的模型（GPT/Luna 系） |
| Nginx + 移植桥接代码 | 全部模型（含 glm/kimi/deepseek 等国产系） |

**建议**：把 Worker 的协议桥接逻辑移植成一个 Node 服务，Nginx 只做 TLS。
**更省事**：直接用 Node 写全部反代（含 `node:https`），一个进程搞定，无需 Nginx。

### 5.4 实施步骤（先验证，后决定是否迁移）

**阶段 0：冻结现状（不改任何配置）**

| 动作 | 记录内容 |
|---|---|
| 记录当前生产状态 | Version ID、域名、路由、密钥名、实际上游 |
| 固定测试请求 | 同一模型、同一请求体、同一账号 |
| 四路同时取证 | 本地日志 + Worker 日志 + OpenCode Console 返回码 + 耗时 |

**阶段 1：VPS 旁路验证（月付、可撤销，勿年付）**

配置不需要高：1–2 vCPU / 1–2 GB 内存 / 够用月流量即可。**重点是网络和 IP，不是 CPU。**

先只部署：TLS、访问控制、最小反代、请求 ID、状态码/耗时/上游错误日志。
**日志不记录 API key 和完整请求体。**

第一阶段**不要**同时引入：住宅 IP、双出口、自动重试、复杂熔断、模型 fallback。

**阶段 2：同请求跨出口 A/B（这是决定性环节）**

固定同一模型 / 同一请求体 / 同一账号，分别经 A（现有 Worker）与 B（新 VPS 出口）发出，观察 **24-72 小时且覆盖晚高峰**：

| 指标 | 通过标准 |
|---|---|
| 403 地区/策略错误 | 新出口显著下降，**且能稳定复现差异** |
| 208 推理池错误 | **不混为一谈**，需单独统计 |
| 首 token 时间 | 不明显恶化 |
| SSE 中途断开 | 无明显增加 |
| 非 2xx 透传 | 状态码与 body 可定位 |
| 密钥暴露 | VPS / 日志 / 客户端均无明文 |
| 国产系桥接 | responses / chat 两条路径分别验证 |

**阶段 3：再决定是否迁移桥接**

只有确认「Worker 仍是主要故障点」才迁移桥接。迁移前必须补：TypeScript 类型检查、固定模型矩阵测试、SSE 完成/截断/异常测试、超时分层测试、真实客户端验收。

| key 隐藏 | ✅ | ✅（需自己实现） | 确定 |
| 受 CF 政策变动影响 | 是 | 否 | 确定 |
| 延迟 | 中（经 CF） | 取决于线路 | 需实测 |
| 跨境丢包 | 存在 | 取决于线路 | **不保证消除** |
| 出口地域型 403 | 存在 | 可能降低 | ⚠️ **待 A/B 验证** |

**结论**：成本换取的是**出口可控性**与**摆脱 CF 节点分配**，这两项是确定的。至于「403 根治」——**在完成 A/B 对照前不能这样承诺**。

### 6.2 双端观测（零成本，收益高）

改掉「只看本地日志」的坏习惯，固定流程：

|---|---|

### 6.3 部署版本核对流程（新增）

**问题**：仓库 master 与线上部署可能长期不一致（当前 master `58c1bc7` 领先线上 `efa996b4` 五个提交）。

**建议流程**：

1. 部署前记录 `wrangler deployments list` 的当前 Version ID；
2. 对照 master 与该 Version 对应的 commit，逐条确认差异是否影响生产行为（差异清单见 `01` 文档第一节）；
3. 部署后重新查询 Version ID 确认变更生效；
4. **不以「仓库已修复」推断「线上已修复」**。

### 6.4 双上游容灾（暂不建议）

目前只有 `opencode.ai/zen/go/v1` 一条路，上游长时间不可用时无路可退。

理论上可在 Worker 加 fallback 映射到第二上游。但这会**增加复杂度**，且对 208 这类秒级失败切换反而可能引入更多问题。**建议先不做**，等真的出现「上游长时间不可用」再考虑。

## 七、决策建议

| 你的情况 | 建议 |
|---|---|
| 偶尔用，链路慢能忍 | 维持现状，CI 已就位 |
| 日常主力，想改善延迟 | 先做零成本验证（换网络/换运营商线路），再决定是否上 VPS |
| 想确认 403 是否与出口有关 | 走阶段 1-2 的月付 VPS A/B，**不要年付** |
| 要完整能力（国产系桥接） | 保留 Worker 桥接层，VPS 只做出口；注意此组合对 403 无效 |
| 不想花钱 | 保持现状，撞 403 时临时切 GPT 系模型 |

**推荐顺序**：

1. ✅ **CI 已落地**（免费，已完成）
2. **零成本验证**：换运营商线路 / 手机热点，确认是否为本地线路问题
3. **观察一周**，统计 403 与跨境错误的实际频率
4. **频率确实影响使用**时，再上**月付可撤销**的 VPS 做 A/B

**不要做的事**：

- ❌ 现在直接弃用 Cloudflare Worker
- ❌ 用纯 Nginx 替代当前桥接（会丢国产系能力）
- ❌ 只因某家 VPS 厂商评测好就年付
- ❌ 把住宅 IP 当作 API 稳定性的默认答案
- ❌ 用自动重试掩盖 208 / 504 / 协议错误
- ❌ 在 A/B 与真实客户端验收前宣布「403 已根治」
