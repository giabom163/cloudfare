## 一、为什么会在 Cloudflare Worker 上做这件事

先讲清动机，不然后面所有取舍都不合理。

### 1.1 起点：OpenCode Go 套餐的真实约束

`opencode.ai/zen/go/v1` 是第三方网关，不是 OpenAI 官方。要用它，绕不开三件事：

| 约束 | 后果 | 谁能解决 |
|---|---|---|
| **key 暴露** | 客户端要直连上游，key 就在 config 里 | Worker |
| **地区封锁** | 国内 IP 直连被 CF 判 403 | 需要能控制出口 |
| **协议分裂** | GPT/Luna 只认 `/responses`，国产系只认 `/chat/completions` | Worker |

前两件是网络问题，第三件是协议问题——**Worker 只解决了第三件，第二件没解决**。

### 1.2 CC Switch 解决不了协议分流

关键约束在 CC Switch 的设计里：

> **apiFormat 是卡级开关，无法按模型分流。**

意思是一张卡上只能设一种协议格式。但 OpenCode 上游要求按模型走不同协议。所以这张卡如果设成 `responses`，glm/kimi/deepseek 全会 400；设成 `chat`，GPT/Luna 全会失败。

**这就是 Worker 存在的唯一理由**：在卡级开关之上，加一层按模型的协议分流。

## 二、四层架构与职责边界

```
┌─────────────────────────────────────────────────────────┐
│ Codex (config.toml + auth.json)                        │
│   只读 ~/.codex/config.toml，不读 cc-switch.db          │
│   base_url = http://127.0.0.1:15721/v1                  │
└────────────────────┬────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────────┐
│ CC Switch (127.0.0.1:15721, Tauri 桌面应用)             │
│   · 注入真 key                                             │
│   · 多卡切换 / usage / 熔断 / 重试                        │
│   ★ 致命限制：apiFormat 是卡级开关，不能按模型分流        │
└────────────────────┬────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────────┐
│ Cloudflare Worker (本项目)                               │
│   · 鉴权透传（传���优先，env key 兜底）                   │
│   · 路径归一化（免疫 /v1 /go /zen 各种拼法）              │
│   · 协议桥接（★ 不可替代的核心价值）                      │
│   · UA 伪装 + session 头注入                              │
│   ✗ 出口 IP 不可控 → 403 地区封锁无解                    │
└────────────────────┬────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────────┐
│ OpenCode 网关 (opencode.ai/zen/go/v1)                    │
│   GPT/Luna/Grok → /responses                            │
│   国产系       → /chat/completions                      │
└─────────────────────────────────────────────────────────┘
```

### 2.1 责任划分表

| 层 | 该做 | 不该做 | 实际踩过的坑 |
|---|---|---|---|
| **Codex** | 只管发请求 | 不该知道 key 是谁的 | 误以为它读 cc-switch.db |
| **CC Switch** | 路由/熔断/usage | **不该承担协议分流**（做不到） | 曾被当作万能中间件 |
| **Worker** | 协议桥接/洗头/传 key | **不该假装成功** | v10 假成功 → v12 回退 |
| **上游** | 推理 | — | 推理池抖动、配额、限流 |

### 2.2 Worker 内部四条路径

| 路径 | 入口 | 适用 | 关键纪律 |
|---|---|---|---|
| 协议桥接 | `handleChatBridge` (L420) | glm/kimi/deepseek/mimo/minimax | responses↔chat 双向，含流式/工具调用/usage |
| 原生透传 | `handleResponsesPassthroughWithRetry` (L967) | GPT/Luna/Grok | 单次 fetch，不重试，不缓冲，错误原样透传 |
| 裸转发 | 内联 (L645-663) | 其余 | 带超时保护 |
| 保活 | `makeResponsesStreamGuard` (L725) | 全部 | 3s keepalive + 60s idle abort |

## 三、协议桥接的原理（最核心的部分）

### 3.1 为什么必须做

```
Codex  ──写 /responses──▶  Worker  ──写 /chat/completions──▶  上游
       ◀──responses SSE──          ◀──chat SSE──
```

两套协议在**请求体、响应体、工具调用、usage 统计**四个维度都不同，必须双向翻译。

### 3.2 模型识别靠前缀，不是能力探测

```ts
const CHAT_MODEL_RE = /^(glm-|kimi-|deepseek-|mimo-|minimax-)/i;
```

代码注释写得很清楚：

> 目录同步会暴露更多模型，但不能仅凭「模型能被列出」推断其协议能力。
> qwen/gpt/grok 及其他未知模型保持 Responses，待能力确认后再加入桥接名单。

**这是有意保守**——宁可漏判走原生（报 400 但看得懂），也不误判走桥接（静默出错难排查）。

### 3.3 桥接的四个翻译点

| 维度 | responses → chat | chat → responses |
|---|---|---|
| 请求体 | `input` → `messages`，`instructions` → system | 反向 |
| 流式事件 | — | `chat.chunk` → `response.output_text.delta` 等 |
| 工具调用 | `function_call` → `tools`/`tool_calls` | 反向，`arguments` 需 JSON 解析还原 |
| usage | `input_tokens`/`output_tokens` | `prompt_tokens`/`completion_tokens` |

对应函数：
- 请求转换：`responsesToChatRequest(rb)`（L426 调用）
- 响应流转换：`makeChatToResponsesStream(model)`（L208 定义，L475 应用）
- 事件守卫：`makeResponsesStreamGuard(model, abort)`（L725）

### 3.4 保活为什么必需

```
上游 30 秒没吐字节
  ↓
Codex SSE 空闲判定 → Reconnecting
  ↓
重连重发整个大上下文（含全部历史）
  ↓
input token 重复计费 ★ 这才是烧额度的真凶
```

解法（L725 guard）：

| 机制 | 频率 | 作用 |
|---|---|---|
| keepalive 注入 | 3s 无数据 | `: keepalive\n\n` SSE 注释，客户端解析器忽略但保连接 |
| idle abort | 60s 无数据 | 真的 hang 了才中断，避免 Worker 实例空转 |
| `seenCompleted` | 一次性 | 防重复发 `response.completed` |

**注意 keepalive 不重置 idle 计时器**——否则一个 hang 住的上游能靠 keepalive 永远不被发现。

## 四、故障分层与排查顺序

### 4.1 关键认知：观测点决定结论

| 观测点 | 能看到 | 看不到 |
|---|---|---|
| `cc-switch.log` | 谁在发、目标 URL、模型名 | **上游返回码** |
| OpenCode Console | 返回码/耗时/token/计费 | 请求来源 |
| `wrangler deployments list` | 线上跑的是哪个版本 | 代码内容 |
| `git log` | 本地代码演进 | 线上是否部署 |

**今天踩的坑**：只看 cc-switch.log 就说「22 点零错误」，被 Console 截图直接推翻（22:03-22:04 大量 `208 inference_failed`）。

**规矩**：本地日志说「发过了」时，**必须去 Console 确认「返回了什么」**。不一致时以 Console 为准。

### 4.2 排查决策树

```
报错
  ↓
Codex 侧: Reconnecting / unexpected status XXX
  ↓
查 cc-switch.log 最后一行
  ├─ 无新行 → CC Switch 没收到请求
  │    ├─ 15721 未监听 → CC Switch 进程死了 → 手动启动
  │    └─ 有请求行但无 FWD-003 → 转发中或已被熔断
  │
  └─ 最后一行是 FWD-003 → 读 upstream_status
       ├─ 403 Country...not supported → CF 边缘地区封锁（换出口 IP）
       ├─ 504 upstream_unavailable → Worker 兜底（可能是代码 bug！查 git）
       ├─ 504 timed out (>60s)      → 上游 60s 无响应（调超时或换模型）
       ├─ 429 GoUsageLimitError     → 周配额打爆（等下周，不可恢复）
       ├─ 429 Token rate limit      → TPM 限流（等窗口自动恢复）
       └─ 401/403 Invalid credential → key 失效或 Authorization 被覆盖
  ↓
查 OpenCode Console 确认实际返回码
  └─ 不一致 → 以 Console 为准（服务端视角）
```

### 4.3 三个「不要」

| 不要 | 后果 |
|---|---|
| 不要用假成功/incomplete 掩盖失败 | Codex 收到「200 但空」→ 表现「没回复=不通」，排查绕大圈 |
| 不要为验证已确认正确的东西发请求 | 每次探测都消耗 token，还可能打爆限流 |
| 不要凭错误文案猜原因 | 「timed out」可能实际是代码崩了（4.1 那次） |

## 五、服务器方案（核心建议）

### 5.1 问题的本质

当前 403 地区封锁的根源：

```
请求 → CF 边缘节点 → CF 按自己的 IP 库判定地区 → 403
```

**你无法控制 Worker 跑在哪个节点、出口 IP 是哪个。** 代码层再怎么改都没用。

### 5.2 五个方案对比

| 方案 | 月成本 | 根治 403 | 延迟 | 保留现有功能 | 评价 |
|---|---|---|---|---|---|
| **A. VPS 自建中转** | ¥30-80 | ✅ 完全 | 低 | ✅ | **最彻底，推荐** |
| B. 换 CF 区域/节点 | ¥0 | ❌ 不可控 | 中 | ✅ | 无效 |
| C. 加腾讯云 EdgeOne | ¥0-50 | ⚠️ 部分 | 低 | ✅ | 需改 DNS，效果不确定 |
| D. 绕过 Worker 直连上游 | ¥0 | ⚠️ 无 403 但也没 Worker | — | ❌ 失去 key 隐藏/协议桥接 | 退回原点 |
| E. Worker + VPS 两层 | ¥30-80 | ❌ Worker 先出口仍 403 | — | ✅ | **钱花了还解决不了** |

**必须提醒的坑**：方案 E 看起来两头兼顾，但 **Worker 那一跳仍会先触发 403**——因为 Worker 自己也要出口到 VPS，白白多加一跳、多花一份钱。**如果目标是根治 403，VPS 必须直连上游。**

### 5.3 方案 A 详细设计

**架构**：

```
Codex
  ↓ 127.0.0.1:15721
CC Switch (多卡/熔断/usage 不变)
  ↓ https://你的域名/v1
VPS 反代 (固定出口 IP)
  ↓
opencode.ai/zen/go/v1
```

**VPS 选型**：

| 项 | 要求 | 说明 |
|---|---|---|
| 位置 | **美区**最稳 / 香港/日本/新加坡 | OpenCode 地区限制 |
| IP 类型 | **住宅/ISP 段最佳** | 数据中心 IP 容易被风控 |
| 线路 | CN2 GIA / 9929 优化 | 国内直连延迟低 |
| 配置 | 1 核 512M 足够 | 纯转发无推理 |
| 系统 | Ubuntu 22.04 / Debian 12 | systemd 简单 |

**反代实现（最简版）**：

```nginx
server {
    listen 443 ssl;
    server_name your.domain.com;

    ssl_certificate     /etc/letsencrypt/live/your.domain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/your.domain.com/privkey.pem;

    location / {
        proxy_pass https://opencode.ai/zen/go/v1;
        proxy_ssl_server_name on;

        # 关键：SSE 必须关缓冲，否则 keepalive 到不了客户端
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 600s;
        proxy_send_timeout 600s;

        # 透传关键头
        proxy_set_header Host              opencode.ai;
        proxy_set_header Authorization     $http_authorization;
        proxy_set_header x-opencode-session $http_x_opencode_session;
        proxy_set_header User-Agent        $http_user_agent;
    }
}
```

**⚠️ 三个必踩的坑**：

1. **`proxy_buffering off;` 必须有** —— Nginx 默认缓冲会把 SSE 卡住，Worker 辛苦发的 keepalive 到不了 Codex，直接 Reconnecting。
2. **`proxy_read_timeout 600s;`** —— 默认 60s 会掐断长推理。
3. **`proxy_set_header Host opencode.ai;`** —— 不改的话上游可能返回 404。

**关于协议桥接**：纯 Nginx 不做 responses↔chat 转换。所以：

| 方案 | 你能用什么 |
|---|---|
| 纯 Nginx | **只有 GPT/Luna 系**（`/responses` 原样走） |
| Nginx + 移植 Worker 代码 | 全部模型（含国产系） |

**建议**：把 Worker 的协议桥接逻辑移植成一个 Node 服务（`serve` 或裸 http 模块），Nginx 只做 TLS。这样能保留全部能力。

**更省事的做法**：直接用 Node 写全部反代（含 TLS 用 `node:https`），一个进程搞定，无需 Nginx。

### 5.4 迁移步骤

| 步骤 | 操作 | 验证 |
|---|---|---|
| 1 | 买美区 VPS，开 443 端口 | `curl -I https://your.domain.com` |
| 2 | 部署反代（Node 或 Nginx） | 直连 VPS 测 `/v1/responses` |
| 3 | **在 Worker 后面加**：CC Switch 卡 `base_url` 改 `https://your.domain.com/v1` | 端到端跑通 |
| 4 | 观察 24h（对比 403 次数） | Console 里 403 归零 |
| 5 | 决定是否弃用 Worker（省一跳） | 视国产系模型是否需要 |
| 6 | Worker 保留作协议桥接入口，VPS 只做出口 | — |

**第 3 步是核心决策点**：两个位置可以放。
- **A. Worker 前置 + VPS 后置**：`Codex → Worker → VPS → 上游`，保留全部功能，但多一跳
- **B. VPS 直连 + 移植桥接**：`Codex → VPS(Node含桥接) → 上游`，少一跳，需移植代码

**如果只想省事不花钱**：保持现状，Worker 继续用，等下次 403 时临时切 gpt 系模型顶一顶。

### 5.5 成本收益

| 项 | 现状 | 方案 A |
|---|---|---|
| 月成本 | ¥0 | ¥30-80 |
| 403 根治 | ❌ | ✅ |
| 出口 IP 可控 | ❌ | ✅ |
| 协议桥接 | ✅ | ✅（移植后） |
| key 隐藏 | ✅ | ✅ |
| 受 CF 政策变动影响 | 是 | 否 |
| 延迟 | 中（经 CF） | 低（直连） |

**结论**：如果 Codex 是日常主力工具，¥30-80/月换「403 根治 + 出口可控 + 不受政策变动影响」是划算的。

## 六、其他一劳永逸措施

### 6.1 CI 编译闸门（成本最低，收益最高）

唯一能防住 P0 代码 bug 的手段。加 `.github/workflows/ci.yml`：

```yaml
name: ci
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22' }
      - run: npm install
      # 关键：tsc 报 TDZ/未定义标识符，esbuild 不报
      - run: npx tsc --noEmit
      # 静态体检：这类 P0 应该被扫出来
      - run: |
          for name in $(grep -oP '(?<=ac\.abort\(\), )[A-Z_]+' src/index.ts | sort -u); do
            if ! grep -q "const $name" src/index.ts; then
              echo "::error::常量 $name 被引用但未定义"; exit 1
            fi
          done
```

**为什么必须用 tsc**：今天这个 bug（`UPSTREAM_TIMEOUT` 未定义）**过了 esbuild（exit=0）但过不了 tsc**。esbuild 不做 TDZ 检查。

### 6.2 双端观测（零成本，收益高）

改掉「只看本地日志」的坏习惯，固定流程：

| 场景 | 动作 |
|---|---|
| 感觉链路断了 | 先查 `cc-switch.log` 最后一行定位到层 |
| 定位到层后 | **必须去 OpenCode Console 确认实际返回码** |
| 两者不一致 | 以 Console 为准 |

### 6.3 双上游容灾（可选）

目前只有 `opencode.ai/zen/go/v1` 一条路。推理池抖动时无路可退。

如果有第二个可用网关，在 Worker 里加 fallback：同一模型名映射到两个上游，失败时切换。

**注意**：这会增加复杂度，且只在「上游长时间不可用」时有用。对 208 抖动这种秒级失败，切换反而可能引入更多问题——**建议先不做**。

## 七、决策建议

| 你的情况 | 建议 |
|---|---|
| Codex 偶尔用，403 能忍 | 维持现状，只加 CI |
| Codex 日常主力，想根治 403 | 走方案 A，VPS 直连 + 移植桥接 |
| 不想花钱但想改善 | 保持现状，撞 403 时切 GPT 系模型 |
| 想要完整能力（国产系 + 不封锁） | Worker 前置 + VPS 后置，接受多一跳 |

**我的建议**：先加 CI（免费、立刻能做），观察一周。如果 403 频率超过每天 10 次，再上 VPS。
