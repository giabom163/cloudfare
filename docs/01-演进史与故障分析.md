## 二、系统原理：它到底在做什么

### 2.1 完整链路

```
Codex (config.toml)
  │  base_url = http://127.0.0.1:15721/v1
  │  wire_api = responses
  ↓
CC Switch (本地路由, 监听 127.0.0.1:15721)
  │  注入真 key、协议格式、熔断/重试/usage
  │  转发到卡内 settings_config.config.base_url
  ↓
Cloudflare Worker (本项目, api.giabom.online/go/v1)
  │  职责：隐藏 key、清洗风险头、补 session、协议桥接
  ↓
OpenCode 网关 (opencode.ai/zen/go/v1)
  │  GPT/Luna 系 → 只认 /responses
  │  国产系 → 只认 /chat/completions
  ↓
模型推理
```

### 2.2 Worker 三个核心职责

**职责一：鉴权透传（L561-563, L592-594）**

```ts
// 客户端（CC Switch）带了 Authorization 就绝不覆盖
if (!bHeaders.get('Authorization')) bHeaders.set('Authorization', `Bearer ${apiKey}`);
```

> **这条是血泪教训**：v3 及之前无条件用 env key 覆盖 Authorization，导致多卡流量全记到 env key 那个账号头上，Go-1 周额度打爆、Go-2 一直显示 0-3%。现在是「透传优先，env key 仅兜底」。

**职责二：路径归一化（L15-24）**

CC Switch 拼 URL 的形态极不稳定，实测出现过 `/responses`、`/v1/responses`、`/go/v1/responses`、`/go/v1/v1/responses`。

```ts
function resolveUpstream(pathname: string): { base: string; apiPath: string } {
  const isZen = /\/zen\//.test(pathname);
  let p = pathname.replace(/\/v1(?=\/|$)/g, '');   // 剥所有 /v1 段
  p = p.replace(/^\/(go|zen)(?=\/)/, '');            // 剥路由标记
  ...
}
```

**职责三：协议桥接（L62-66, L420）**

CC Switch 的 apiFormat 是**卡级开关，无法按模型分流**，所以协议分流只能在 Worker 做：

```ts
const CHAT_MODEL_RE = /^(glm-|kimi-|deepseek-|mimo-|minimax-)/i;
```

命中则 `/responses` → `/chat/completions`，再把响应（含 SSE 流、工具调用、usage）转回 responses 格式。

### 2.3 三条路径的分工

| 路径 | 入口函数 | 适用模型 | 行为 |
|---|---|---|---|
| 协议桥接 | `handleChatBridge` (L420) | glm/kimi/deepseek/mimo/minimax | responses↔chat 双向转换 |
| 原生透传 | `handleResponsesPassthroughWithRetry` (L967) | GPT/Luna/Grok | 单次 fetch，`stream:true` 原样发，非 200 原样透传 |
| 裸转发 | 入口内联 (L645-663) | 其余 | 带超时保护的直转 |

**原生透传路径的关键纪律**（v12 确立，至今未变）：
- 不重试
- 不缓冲成 `stream:false`
- 不返回假成功 `incomplete`
- 上游非 200 → 原样透传状态码和 body，由 Codex 自行处理

### 2.4 保活机制（L725 `makeResponsesStreamGuard`）

上游长时间无字节会让 Codex 判定 SSE 空闲断连 → Reconnecting → **重连重发整个大上下文 = input 重复计费**（这才是烧额度的真凶）。

```ts
const UPSTREAM_IDLE_TIMEOUT = 60_000;  // L722 上游流空闲上限
// 3 秒无数据 → 注入 SSE 注释行 keepalive
// 60 秒无数据 → abortUpstream() + controller.error
// seenCompleted 标志防重复发 response.completed
```

## 四、哪里容易出问题（按踩坑频率排序）

### 4.1 🔴 P0：改动一个常量，忘改引用点

**今天刚发生的实例。**

`6083d4b` 把 `UPSTREAM_TIMEOUT` 改名为 `UPSTREAM_HEADERS_TIMEOUT`，但只改了透传分支（L974），**漏了桥接分支 L431 和裸转发分支 L647**：

```ts
L431  setTimeout(() => ac.abort(), UPSTREAM_TIMEOUT)  // ← 常量已不存在
L647  setTimeout(() => ac.abort(), UPSTREAM_TIMEOUT)  // ← 常量已不存在
```

**后果放大机制**：ReferenceError 被 L450 的 `catch` 捕获，而那段代码返回的是：

```
504 { error: 'upstream_unavailable', message: 'chat upstream timed out or unreachable (>60s)' }
```

**错误文案彻底误导** —— 不是超时，是代码崩了。所有国产系模型（glm/kimi/deepseek/mimo/minimax）会全部 504。

**为什么没立刻发现**：
1. esbuild **不会**因 `const` TDZ 报错（esbuild 4.144 实测 `exit=0`）
2. 该提交从未部署，所以线上没受影响
3. 直到今天第一次调 `glm-5.3-flash` 才暴露

**预防措施**：改常量名后立刻全局搜引用，`grep -n "旧名"` 必须为 0。

### 4.2 🔴 P0：Cloudflare WAF 地域封锁

```
403 Country, region, or territory not supported
```

CF 边缘**按出口 IP 判定地区**，请求根本没到上游。实测本机这种情况一天出现 6 次（20:45）。

**本机现状**（实测）：**无任何翻墙环境**
- system proxy `ProxyEnable = 0`（关）
- `ProxyServer = 127.0.0.1:7897` 是**残留死配置，该端口无人监听**
- `HTTP_PROXY = http://127.0.0.1:51155` 指向 `sandbox-cli`——那是 WorkBuddy 沙箱自己的代理，不是翻墙
- clash/v2ray/sing-box/Watt 进程一个都没有
- `chatgpt.com` / `api.openai.com` / `auth.openai.com` / `openai.com` DNS 全部 **ECONNREFUSED**

**注意**：这个 403 的判定发生在 Cloudflare 边缘，**Worker 代码层改不了**。

**⚠️ 归因边界（重要）**：

403 的文案是 `Country, region, or territory not supported`，**它确实指向出口地域判定，但本项目尚未完成同请求跨出口 A/B 对照**，因此严格说这是**已观察到的候选原因，而非已证实的根因**。要确证，需要：

1. 同一请求体、同一模型、同一账号，分别经不同出口发出；
2. 若 403 只在特定出口出现，才可归因于出口地域；
3. 若 403 在所有出口都出现，则应转向请求头、鉴权、路径、上游权限或 WAF 规则方向排查。

**同类需要 A/B 归因的错误**：`401/403 Invalid credential`（也可能来自 Worker 覆盖 Authorization，而非 key 失效）。

### 4.2b 🔴 P0：跨境链路质量（2026-10-06 新增，与代码无关）

**症状与代码 bug 完全不同**，不要混淆：

| 现象 | 含义 |
|---|---|
| `error sending request` | 请求根本没发出去（连接层失败） |
| `请求超时: error sending request` | 同上，触发了 CC Switch 超时 |
| `流错误: error decoding response body` | **响应体传到一半被切断** |
| 体感：极慢 + 频繁失败，但非全断 | 典型链路质量差 |

**2026-10-06 实测数据**：

```
TCP 443 握手      正常（200-290ms，0% 丢包）
ICMP ping         213ms，0% 丢包
TLS 握手          极不稳定（8 采样 4 次 TIMEOUT，HTTP 层出现 24295ms 后 ECONNRESET）
tracert           219.158.x.x = 中国联通骨干
                  第 4-7 跳全无响应、第 11-12 跳全无响应
```

**结论**：不是被墙，是**运营商到境外这一段丢包**。小包（ICMP/TCP 握手）通，大包（TLS 握手、响应体）丢。

**已验证的无效手段**（重要，避免重复踩）：

| 手段 | 实测结果 | 原因 |
|---|---|---|
| **换 DNS** | ❌ 无效，且更慢 | 7 个 DNS 返回的 IP 集合完全相同；DNS 只决定「给你哪几个 IP」，不决定「走哪条路去」 |
| **换 A 记录 IP** | ❌ 治不了根 | `api.giabom.online` 两个 A 记录都被 CF 分到 LAX；新 IP TLS 稳但 HTTP 慢，旧 IP 反之 |
| **开 Watt 加速** | ❌ 无关 | Watt 是 hosts 劫持，只劫持其配置域名（本机是 GitHub 那批），对 Worker / 上游零作用 |

**唯一有实证支持的方向**：改变出口路径（VPS / 代理）或更换本地运营商线路。详见 `02-架构原理与服务器方案.md`。

### 4.3 🟠 P1：上游推理池抖动（不限于 GLM）

```
208 { error: 'inference_failed' }   耗时仅 2-3 秒，Tokens/Cost 均为 —
```

上游推理池分配不到算力立刻拒。特征：**极快失败 + 零 token 消耗**。实测 22:03-22:04 失败率约 80%。

**好消息**：不计费，切换模型/卡即可规避。

### 4.4 🟠 P1：60 秒超时吃掉长请求

```
504 chat upstream timed out or unreachable (>60s)
```

实测 20:48-21:18 持续 40 分钟约 88 次，并触发 `CB-004 熔断器 连续失败 8 次 → Open`。

**候选根因（尚未通过分阶段计时确证）**：

超时现象可能来自多条路径，**当前日志不足以单独归因**：

| 候选 | 说明 | 如何验证 |
|---|---|---|
| 上游推理池本身慢或拒绝 | 平台侧算力不足 | 对比不同模型/时段的成功率 |
| 等响应头阶段超时 | 上游根本没开始响应 | 记录「发出到收到首字节」耗时 |
| 流已建立但无数据 | 上游生成中长时间静默 | 记录首字节后到下一个字节的间隔 |
| Cloudflare 平台限制 | Worker CPU / 连接时长约束 | 分阶段计时对照 |
| 本地客户端 / 中间代理读超时 | 链路层提前断开 | 结合 `error decoding response body` 判定 |

**设计上的取舍**：超时设短了会误杀正常请求，设长了 Worker 实例被长时间占用。`6083d4b` 把它拆成三段（headers / idle / keepalive）正是为了分别处理这三类，**但「三段各自的阈值是否最优」仍需真实负载数据验证**。

**当前三段式设计**（6083d4b 引入，master 已修 TDZ）：

| 阶段 | 计时器 | 值 | 作用 |
|---|---|---|---|
| 等响应头 | `UPSTREAM_HEADERS_TIMEOUT` | 60s | 拦「上游根本不回」 |
| 流建立后空闲 | `UPSTREAM_IDLE_TIMEOUT` | 60s | 拦「流开了但数据不来」 |
| 客户端侧 | `makeResponsesStreamGuard` keepalive | 3s | 降低客户端误判断连的概率 |

**⚠️ 关于 keepalive 的准确定位**：SSE 注释行 keepalive 只是**降低误判断连的手段**，不构成长请求可靠性的证明。它不能保证：Cloudflare 到上游的连接不被平台限制、中间代理一定转发注释行、客户端一定不重连。

### 4.5 🟠 P1：SSRF 观测盲区（今天犯的错）

**CC Switch 本地日志看不到上游返回码。**

`cc-switch.log` 里 `[Codex] >>> 请求目标: ...` 只代表**请求已发出**。上游返回 200/403/504/208 它一概不记，只有非 2xx 时才额外打一条 `FWD-003`。

今天我据此说过「22 时段零错误」，用户直接甩来 OpenCode Console 截图推翻——22:03-22:04 明明有大量 `208 Failed`。

**判定链路是否真断必须双端对照**：
- 本地：`cc-switch.log`（谁在发、什么时候发）
- 服务端：OpenCode Console（返回什么、耗时多少、计费多少）

### 4.6 🟡 P2：熔断器放大

```
CB-004 熔断器触发: 连续失败 8 次 → Open
```

熔断后一段时间内**全部请求直接失败**，期间即使上游已恢复。阈值从 4 调到 8 就是为了扛住这个。

**排查陷阱**：熔断打开时看到的 504 大多不是上游真挂了，是熔断的余波。

### 4.7 🟡 P2：429 的两种性质

必须分清，否则方向全错：

| 类型 | 特征 | 恢复方式 |
|---|---|---|
| **周配额耗尽** | `GoUsageLimitError` + `metadata.limitName: "weekly"` | 等周窗口重置（不可恢复） |
| **Token 速率限流** | `Token rate limit exceeded` / `type: too_many_requests` | 分钟窗口自动恢复 |

判别方法：读 `provider_health.last_error` 和 `proxy_request_logs.error_message`，别只看文案。

### 4.8 故障汇总表

| 层 | 故障 | 症状 | 本层能否解决 |
|---|---|---|---|
| CF 边缘 | 地区封锁 | `403 Country...not supported` | ❌ 需换出口 IP |
| CF 边缘 | WAF 拦指纹 | `1020 Access denied` | ⚠️ 伪装 UA |
| Worker | 常量未定义 | `504 upstream_unavailable`（伪装成超时） | ✅ 改代码 |

## 六、一劳永逸的方案

### 6.1 先分清哪些能确定性解决、哪些不能

**「确定性能否解决」比「是否值得试」更重要。** 分类如下：

| 故障 | 确定性 | 方向 | 备注 |
|---|---|---|---|
| 常量未定义 / TDZ | ✅ 可确定性消除 | CI 闸门（已落地，见 6.2） | 有回归测试实证 |
| 熔断放大 | ✅ 可确定性消除 | 阈值 + 退避策略 | 已将阈值调至 8 |
| 观测盲区 | ✅ 可确定性消除 | 双端对照（见 6.4） | 零成本 |
| 硬编码密钥 | ✅ 可确定性消除 | guard 检查（已落地） | — |
| **出口地域型 403** | ⚠️ **待 A/B 验证** | 换出口 IP / 服务器 | **不能承诺根治**，见 6.3 |
| **跨境链路质量** | ⚠️ **部分可改善** | 换路径 / 换运营商 | 无法消除运营商丢包 |
| 上游推理池抖动 | ❌ 不可控 | 只能换模型/卡规避 | 上游策略 |
| 上游配额 / 限流 | ❌ 不可控 | 等窗口 / 等周重置 | 上游策略 |

**关于「出口地域型 403」的准确表述**：

- 如果 403 确由 Cloudflare / 上游按出口 IP、国家或地区拒绝，换到被接受的出口**可以降低这一类 403 的发生率**；
- **不能保证永久解决**——出口 IP 可能被封、被标记、进入风控名单，或策略本身发生变化；
- 如果 403 实际来自请求头、鉴权、路径、上游权限或 WAF 规则，**换 VPS 不会有任何帮助**；
- **在完成同请求跨出口 A/B 对照之前，不应把它写成「已根治」。**

### 6.2 已落地：CI 编译闸门

**这是唯一能确定性防住 4.1 那类 P0 的手段，已于 2026-10-06 落地并通过回归测试。**

已加入仓库的文件：

| 文件 | 作用 |
|---|---|
| `.github/workflows/ci.yml` | install → typecheck → guard → bundle:check；deploy job `if: false` 锁死 |
| `scripts/guard.mjs` | 6 项零误报体检（常量声明、TDZ、顶层重复、硬编码密钥、`.dev.vars` 未跟踪、关键常量齐全） |
| `package.json` | `typecheck` / `guard` / `check` / `bundle:check` 脚本 + typescript / esbuild 依赖 |

**为什么必须用 `tsc` 而不是 esbuild**（已实测）：

| 检查 | 注入 TDZ 缺陷后的结果 |
|---|---|
| `esbuild --bundle` | `exit=0` ✅ **通过**（实测 esbuild 0.28.1 不做 TDZ 检查） |
| `tsc --noEmit` | `exit=2` ❌ 3 处全报 `TS2552` |
| `scripts/guard.mjs` | `exit=1` ❌ 7 项违规 |

**CI 的边界（必须清楚）**：

CI 只能拦**编译期错误**。以下拦不住：

| 拦不住 | 为什么 |
|---|---|
| 跨境链路慢 / 丢包 | 不是代码问题 |
| 出口地域型 403 | 需换出口 + A/B 验证 |
| 上游推理池抖动 | 上游服务状态 |
| **逻辑写错**（如引入重试/假成功） | 需人工代码评审 |
| 熔断阈值调错 | 需运行监控告警 |

**CI 是底线，不是天花板。**

**关键点**：`tsc --noEmit` 会把 TDZ / 未定义标识符报出来，而 **esbuild 不会**。今天这个 bug 过了 esbuild 但过不了 tsc。

### 6.3 彻底解决 403 地区封锁：换服务器 / 换出口

**这是本项目最大的结构性缺陷。** Worker 跑在 CF 全球节点，出口 IP 由 CF 分配，你无法控制它落在哪个地区。

**方案对比**：

| 方案 | 成本 | 能否解决 403 | 延迟 | 说明 |
|---|---|---|---|---|
| **A. 换国内可直连的海外 VPS 自建中转** | ¥30-80/月 | ✅ 完全可控 | 低 | 最彻底，出口 IP 固定 |
| B. Cloudflare Workers + 换区域 | 免费 | ❌ 不可控 | 中 | Workers 节点由 CF 分配 |
| C. 加一层国内可直连的 CDN（如腾讯云 EdgeOne） | ¥0-50/月 | ⚠️ 部分 | 低 | 需改 DNS |
| D. 直连上游 + 本地 CC Switch（不过 Worker） | ¥0 | ❌ 但无 403 | — | 放弃 key 隐藏与 UA 伪装 |

**方案 A 详细（推荐）**：

```
Codex → CC Switch (127.0.0.1:15721)
       → 你的 VPS (自有域名, 固定 IP)
       → opencode.ai/zen/go/v1
```

VPS 只需跑一个极简 Node/Python 反代（Nginx 也可）。选型需**逐项验证而非默认可行**：

| 项 | 需要确认什么 | 为什么不能默认 |
|---|---|---|
| 出口地区 | **先确认上游实际接受哪些地区** | 不能默认「美区最稳」；上游策略可能变化 |
| 账号绑定 | 你的账号 / 套餐是否绑定地区 | 换出口未必解决账号侧限制 |
| IP 类型 | 数据中心 IP 是否被目标服务标记 | IP 段信誉影响风控，非标签决定 |
| 线路质量 | 到上游稳定 + 到本地客户端可用 | 两个方向都要满足 |
| 国内直连延迟 | 晚高峰是否稳定 | 「低延迟」≠「稳定」 |

**成本**：`¥30-80/月` 是**基于公开 VPS 价格的粗略区间估算，不是本项目实测数据**。实际价格随地区、线路、带宽、是否含 IP 而显著变化。月付、可退款、可换实例是优先条件。

**能预期的收益**（按确定性排序）：

| 收益 | 确定性 |
|---|---|
| 出口 IP 固定可控 | ✅ 确定 |
| 不受 Cloudflare 节点分配策略影响 | ✅ 确定 |
| 减少跨境路由绕路 | ✅ 较确定 |
| 降低出口地域型 403 发生率 | ⚠️ 待 A/B 验证 |
| 完全消除跨境丢包 | ❌ 不保证（取决于线路） |

**Worker 保留的理由**：key 隐藏、多卡切换、协议桥接、UA 伪装这些逻辑仍在 Worker 层更合适。也可组合：

```
Codex → CC Switch → Worker (协议/key) → VPS (换出口) → 上游
```

**⚠️ 这个组合对 403 无效**：Worker 那一跳自己也要出口，仍可能在 Worker 处被 403 拦下。它只适用于「只想要固定出口、不需要解决 403」的场景。要针对 403 验证效果，**VPS 必须直连上游**。

### 6.4 观测修正：双端对照（已确立，零成本）

**这是 4.5 的解法，成本为零。**

| 观测点 | 能看到 | 看不到 |
|---|---|---|
| `cc-switch.log` | 谁在发、目标 URL、模型名 | **上游返回码** |
| OpenCode Console | 返回码、耗时、token、计费 | 请求来源 |

**用法**：本地日志说「发过了」时，**必须去 Console 确认「返回了什么」**。两者不一致时，以 Console 为准（它是服务端视角）。

**已验证的价值**：2026-10-06 排查「GPT 变慢」时，若只看 `cc-switch.log` 会看到「请求正常转发」而误判为正常；Console 显示的是 `error decoding response body`，两者结合才定位到链路层。

### 6.5 中长期架构建议

```
① 网络层：VPS 固定出口（待 A/B 验证效果）
② 路由层：CC Switch 多卡 + 熔断阈值 8（已做）
③ 协议层：Worker 做 responses↔chat 桥接（保留）
④ 观测层：双端对照 + usage 看板
⑤ 质量闸门：tsc + guard 进 CI（已落地，回归测试通过）
```

**不建议做的**：
- ❌ 不要试图在 Worker 里 hack 掉 403（CF 边缘层，Worker 改不了）
- ❌ 不要用假成功/incomplete 掩盖失败（已废弃，会导致 Codex 空回复且排查绕圈）
- ❌ 不要为省事把熔断阈值调回 4（40 分钟故障的实测说明 8 更稳）
- ❌ 不要把「仓库已修复」当成「线上已修复」——**两者是不同证据面**
- ❌ 不要用自动重试掩盖 208 / 504 / 协议错误（会掩盖真实故障率）
